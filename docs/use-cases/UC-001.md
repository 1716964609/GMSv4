# UC-001 — Translate Text

**Status:** Draft

**Version:** 0.2

## 1. Overview

**Primary Actor:** Operator

**Goal:**

Translate Original Text using DeepL and GPT while applying terminology from the currently Uploaded Glossary.

The translation is considered successful only after both translation stages and the required glossary persistence operation have completed successfully.

**Linked Requirements:**

- FR-001 — Source Text Input
- FR-002 — Machine Translation Provider
- FR-003 — LLM Provider
- FR-004 — Glossary Upload and Accumulation
- FR-005 — Glossary-Aware Machine Translation
- FR-006 — Glossary-Aware LLM Post-Editing
- FR-007 — Translation Output
- C-002 — Canonical Glossary Entry
- C-003 — Database Scope
- C-004 — No Translation History

---

## 2. Preconditions

- The Operator can access the application through a web browser.
- No authentication or user registration is required.
- The application provides an input field for Original Text.
- The Operator can specify source and target languages.
- The application supports optional JSON Glossary uploads.

---

## 3. Trigger

The Operator clicks the Submit button to request translation.

The Submit button is disabled when the Original Text is empty.

---

## 4. Main Success Scenario

1. The Operator enters Original Text into the browser text box.

2. The Operator specifies the source and target languages.

3. The Operator optionally uploads a JSON Glossary file containing Glossary Entries.

4. If a Glossary is uploaded, the frontend checks its JSON structure and displays an error if the file is invalid.

5. The application enables the Submit button when the Original Text is not empty and the available input passes frontend validation.

6. The Operator clicks Submit.

7. The frontend submits the Translation Request to the backend.

8. The backend independently validates the submitted input, including the JSON Glossary when provided.

9. The application provides the following inputs to DeepL:
   - Original Text
   - Source language
   - Target language
   - Terminology from the current Uploaded Glossary, when provided

10. DeepL performs glossary-aware machine translation and produces the Intermediate Translation.

11. The application provides the following inputs to GPT:
    - Original Text
    - Intermediate Translation
    - Terminology from the current Uploaded Glossary, when provided

12. GPT performs translation post-editing to improve translation quality and align the translated text with the specified terminology.

13. GPT produces the Final Translation.

14. If a Glossary was uploaded, the application appends its Glossary Entries to the persistent Glossary database.

15. If a Glossary was uploaded, the application confirms that the required database operation has completed successfully.

16. The backend returns a successful translation response containing the Final Translation.

17. The frontend displays the Final Translation and informs the Operator that translation has completed successfully.

18. The application provides a Download button for saving the Final Translation as a TXT file.

---

## 5. Alternative Flows

### A1 — Empty Original Text

**Trigger:** The Original Text is empty before submission.

1. The Submit button remains disabled.
2. The Operator cannot initiate the Translation Request.

### A2 — No Glossary Uploaded

**Trigger:** Step 3. The Operator does not upload a Glossary.

1. The application skips the glossary-specific validation in Step 4 and proceeds to Step 5.
2. The application enables the Submit button when the Original Text is not empty and the available input passes frontend validation.
3. The Operator clicks Submit, and the application continues through backend validation in Step 8 without a Glossary to validate.
4. The application proceeds through Steps 9–13: DeepL produces the Intermediate Translation, and GPT performs post-editing to produce the Final Translation.
5. The application skips the glossary persistence operation in Step 14 and the corresponding confirmation in Step 15.
6. The application continues at Step 16 of the Main Success Scenario.

### A3 — Download Final Translation

**Trigger:** The Final Translation is displayed after successful processing.

1. The Operator clicks the Download button.
2. The application downloads the Final Translation as a TXT file.

---

## 6. Exception Flows

### E1 — Invalid Glossary File

**Trigger:** Step 4 or Step 8. The uploaded Glossary is not valid JSON or does not conform to the required structure.

1. The application rejects the invalid Glossary.
2. If the error is detected by the backend, the backend returns an input-validation error response.
3. The frontend displays an understandable error message.
4. The Operator can correct or replace the Glossary file.
5. Translation does not proceed while the submitted Glossary is invalid.
6. No Glossary Entries are appended to the database.

### E2 — Invalid Backend Input

**Trigger:** Step 8. The backend receives invalid input, including an empty Original Text.

1. The backend rejects the Translation Request.
2. The backend returns an input-validation error response.
3. The frontend displays an understandable error message.
4. No translation is performed.
5. No Glossary Entries are appended to the database.

### E3 — DeepL Translation Failure

**Trigger:** Step 10. DeepL fails to produce the Intermediate Translation.

1. The application stops the translation process.
2. GPT post-editing is not executed.
3. The backend returns an error response.
4. The frontend informs the Operator that translation could not be completed.
5. No Final Translation is produced or returned.
6. No Glossary Entries are appended to the database.

### E4 — GPT Post-Editing Failure

**Trigger:** Step 13. GPT fails to produce the Final Translation.

1. The application stops the translation process.
2. The Intermediate Translation is not returned as the Final Translation.
3. The backend returns an error response.
4. The frontend informs the Operator that translation could not be completed.
5. No Final Translation is returned.
6. No Glossary Entries are appended to the database.

### E5 — Glossary Database Persistence Failure

**Trigger:** Step 14 or Step 15. The application fails to complete the required Glossary persistence operation.

1. The application treats the entire Translation Request as unsuccessful.
2. The database append operation must not leave a partially appended set of entries.
3. The backend returns an error response.
4. The frontend informs the Operator that translation could not be completed.
5. The Final Translation is not returned to the Operator.
6. The frontend does not display a successful translation result.
7. The Download button is not enabled for the failed Translation Request.

---

## 7. Postconditions

### 7.1 Successful Translation

- DeepL has successfully produced the Intermediate Translation.
- GPT has successfully produced the Final Translation.
- If a Glossary was uploaded, all its entries have been successfully appended to the persistent Glossary database.
- Previously stored Glossary Entries remain unchanged.
- The backend has returned a successful response containing the Final Translation.
- The Final Translation is displayed in the browser.
- The Final Translation can be downloaded as a TXT file.
- Original Text, Intermediate Translation, and Final Translation are not stored in the application database.

### 7.2 Failed Translation

- The application returns an error response.
- The frontend displays an understandable error message.
- No successful Final Translation is returned for the failed request.
- No new Glossary Entries remain appended as a result of the failed request.
- Previously stored Glossary Entries remain unchanged.

---

## 8. Business Rules

### BR-001 — Current Glossary Only

Only Glossary Entries from the current Uploaded Glossary are used for the current Translation Request.

Previously stored Glossary Entries are not retrieved or used to influence the current translation.

### BR-002 — Sequential Translation

Translation consists of two sequential processing stages:

1. DeepL generates the Intermediate Translation.
2. GPT performs post-editing and generates the Final Translation.

The second stage must not execute unless the first stage completes successfully.

### BR-003 — Terminology Alignment

Both translation stages receive terminology from the current Uploaded Glossary when provided.

GPT must be instructed to follow the user-specified target terminology when applicable.

The application relies on the translation providers' capabilities and instructions to achieve terminology alignment.

The application does not perform deterministic post-translation terminology validation.

### BR-004 — Glossary Accumulation

Glossary Entries from the current Uploaded Glossary are appended to the persistent Glossary database only after both translation stages complete successfully.

Previously stored entries are not deleted or replaced.

No automatic terminology conflict-resolution or deduplication rules are applied.

### BR-005 — Translation Success Gate

A Translation Request is considered successful only when:

1. DeepL successfully produces the Intermediate Translation.
2. GPT successfully produces the Final Translation.
3. The required Glossary database persistence operation completes successfully, when a Glossary was uploaded.

The Final Translation must not be returned as a successful result before these conditions are satisfied.

When no Glossary is uploaded, no database append operation is required.

### BR-006 — Atomic Glossary Persistence

When multiple Glossary Entries are appended to the database for one Translation Request, the operation must be atomic.

Either all entries from the current upload are appended successfully, or none of them are appended.

A failed append operation must not modify previously stored Glossary Entries.

### BR-007 — Transient Translation Data

Original Text, Intermediate Translation, Final Translation, and Translation Requests must not be stored persistently in the application database.

Only Glossary data may be stored persistently.

### BR-008 — Glossary JSON Structure

An Uploaded Glossary is represented as a JSON array of Glossary Entry objects.

Example:

```json
[
  {
    "source_term": "heart failure",
    "target_term": "心不全",
    "source_lang": "EN",
    "target_lang": "JA"
  },
  {
    "source_term": "hypertension",
    "target_term": "高血圧",
    "source_lang": "EN",
    "target_lang": "JA"
  }
]
```

Each Glossary Entry must contain exactly four canonical fields:

- `source_term`
- `target_term`
- `source_lang`
- `target_lang`

All four fields are required and must contain string values.

An empty JSON array is permitted and provides no glossary terminology.

### BR-009 — Glossary Input Validation

The frontend may validate the uploaded JSON file before submission to provide immediate feedback.

The backend must independently validate all submitted input.

Frontend validation must not be treated as a trusted security or correctness boundary.

Invalid JSON or a structurally invalid Glossary must be rejected.

The application does not perform automatic linguistic language detection or verify that the actual text of each term matches its declared language.

### BR-010 — Error Handling

The backend must return an error response when a Translation Request fails.

The frontend must display a clear and understandable error message.

For translation-service or database failures, the message should advise the Operator to contact the administrator or report the issue if it persists.

The application must not expose internal exception details, API credentials, or other sensitive implementation information in user-facing error messages.

The application does not require a large set of custom error codes.

### BR-011 — No Partial Translation Result

The Intermediate Translation must never be presented as the successful Final Translation.

If any required processing stage fails, the Translation Request must be treated as unsuccessful.

No successful Final Translation may be returned before the Translation Success Gate is satisfied.
